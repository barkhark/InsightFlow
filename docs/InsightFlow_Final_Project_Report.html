1. INTRODUCTION

1.1 EXISTING SYSTEM, PROPOSED SYSTEM AND NEED AND OBJECTIVE OF SYSTEM

Existing System

In traditional institutional and university environments, academic and administrative service delivery is often fragmented across multiple disparate channels. Students seeking transcript verifications, grade sheet re-evaluations, fee installment approvals, hostel room allotments, or IT infrastructure support typically rely on physical paper application forms, unstructured email threads, or informal desk inquiries. This operating paradigm presents several structural weaknesses:

  • Lack of Centralized Status Visibility: Students submit paperwork or emails without any transparent mechanism to trace which department, officer, or workflow stage currently holds their request.
  • Fragmented Departmental Coordination: Departments operate as isolated administrative silos with independent spreadsheets and physical ledgers, making cross-departmental coordination cumbersome.
  • Absence of Deterministic SLA Tracking: Institutional service level targets exist primarily as guidelines without real-time tracking, resulting in requests languishing unnoticed until manually escalated.
  • Lack of Auditability and Accountability: When delays or oversights occur, it is difficult to identify whether bottleneck dwell time stems from staff workload, missing documentation, or processing latency.
  • Deficit of Actionable Operational Intelligence: Institutional directors lack empirical dashboards revealing department compliance rates, stage bottleneck hotspots, or recurring service failure categories.

Proposed System: InsightFlow

InsightFlow is a decoupled, role-governed web application designed to centralize and automate university service workflows while enforcing deterministic SLA accountability. The platform integrates a modern React single-page frontend with a Django REST Framework backend, supported by a structured relational database architecture.

InsightFlow provides pre-configured multi-tenant routing across 8 academic and administrative departments (Academic Administration, Examination Cell, Facilities & Maintenance, Finance & Accounts, Hostel & Student Affairs, IT Services, Library Services, and Transport Services). The system implements 42 granular service categories governed by 3 distinct workflow state machines (Administrative Approval, Certificate Issuance, and Issue Resolution) comprising 13 discrete lifecycle stages. Crucially, every transition is validated atomically, tracked via stage dwell history, logged into an append-only immutable audit ledger, and monitored by a deterministic mathematical SLA engine.

Need of the System

Higher educational institutions require a reliable, transparent bridge between student requests and administrative fulfillment. Eliminating physical bottlenecks and informal escalation pathways directly enhances student satisfaction, accelerates administrative turnaround times, and provides institutional governance with authentic operational transparency.

Objectives of the System

  • Automated Request Management: Automate institutional request intake across 8 university departments using dynamic JSON-based form schemas tailored to 42 granular service categories.
  • Departmental Isolation & Security: Enforce strict Role-Based Access Control (RBAC) isolating Student, Staff, and Administrator capabilities while restricting departmental staff access to authorized queues.
  • Deterministic SLA Accountability: Calculate real-time stage dwell times and deterministic warning/critical SLA breach thresholds without black-box opacity.
  • Immutable Governance Audit Trail: Maintain an append-only, tamper-evident audit ledger recording every stage transition, note, and assignment timestamp.
  • Executive Analytics & Telemetry: Provide university leadership with interactive dashboards measuring department compliance rates, stage congestion, and multi-metric CSAT satisfaction ratings.

1.4 DESCRIPTION OF TECHNOLOGY USED

InsightFlow was engineered using a curated technology stack chosen specifically for stability, academic rigor, and modular decoupling:

  • Python: Python provides high readability, clean object-oriented architecture, and robust native data manipulation libraries ideal for building decoupled workflow and mathematical SLA calculation engines.
  • Django 4.2 LTS: Django serves as the core web application backbone, delivering an enterprise-grade Object-Relational Mapper (ORM), secure database migrations, native password hashing (PBKDF2 SHA-256), and atomic transaction controls.
  • Django REST Framework: DRF facilitates the development of clean, standardized RESTful endpoints with serializer-driven validation, consistent JSON response envelopes, object-level permission enforcement, and configurable rate throttling.
  • SimpleJWT: SimpleJWT implements stateless token-based authorization. Access tokens (60-minute lifespan) and refresh tokens (7-day lifespan) permit decoupled client-server authentication without server-side session locks.
  • React 19: React enables a responsive, component-driven user interface. Declarative state management and hooks (useState, useEffect, useContext) provide dynamic form rendering and instant UI feedback.
  • Vite 8: Vite provides lightning-fast Hot Module Replacement (HMR) and optimized Rollup-based asset bundling for zero-latency development and efficient client delivery.
  • React Router DOM: React Router DOM facilitates declarative, client-side route navigation with role-guarded route components (ProtectedRoute) that enforce client-side access control.
  • SQLite 3 Database: SQLite 3 provides a lightweight, zero-configuration relational database engine embedded directly within the project repository (db.sqlite3). The application maintains full PostgreSQL compatibility via settings/base.py and psycopg2-binary.

5.3 IMPLEMENTATION DETAILS

InsightFlow was implemented using clean layered separation of concerns:

  • Service Layer: Pure Python services (WorkflowEngine, SLAEngine, PredictiveEngine) encapsulate business logic independently of Django HTTP controllers.
  • Atomic Transactions: All database writes modifying stage positions execute inside django.db.transaction.atomic() context managers, ensuring that RequestStageHistory closures and AuditRecord inserts commit together.
  • API Consistency: Standardized custom exception handler formats all client responses into a uniform envelope: {success: bool, data: {...}, error: {...}}.

6.1 Atomic Workflow Transition Logic (core/workflow_engine.py)

The WorkflowEngine encapsulates atomic lifecycle transitions, closing previous stage duration history and recording immutable audit entries:

@transaction.atomic
def execute_transition(self, service_request, target_stage, actor, note=""):
    # 1. Validate legality
    can_move, reason = self.can_transition(service_request, target_stage, actor)
    if not can_move:
        raise WorkflowValidationError(reason)

    old_stage = service_request.current_stage
    now = timezone.now()

    # 2. Close current stage history
    current_history = service_request.stage_history.filter(exited_at__isnull=True).first()
    if current_history:
        current_history.exited_at = now
        dwell_secs = (now - current_history.entered_at).total_seconds()
        current_history.duration_minutes = round(dwell_secs / 60)
        current_history.save()

    # 3. Update ServiceRequest
    service_request.current_stage = target_stage
    service_request.stage_entered_at = now
    if target_stage.is_terminal:
        service_request.status = 'rejected' if target_stage.is_rejection else 'resolved'
        service_request.resolved_at = now
    else:
        service_request.status = 'in_progress'
    service_request.save()

    # 4. Create new stage history & immutable audit record
    RequestStageHistory.objects.create(request=service_request, stage=target_stage, entered_at=now, transitioned_by=actor)
    AuditRecord.objects.create(request=service_request, actor=actor, action='STAGE_TRANSITION',
                               description=f'Moved to {target_stage.name}', is_student_visible=True)
    return service_request

Significance: Enforces transactional atomicity and append-only governance, ensuring that request state, dwell history, and audit records never drift out of sync.

6.2 Deterministic SLA & Health Calculation (core/sla_engine.py)

The SLAEngine performs mathematical evaluation of stage dwell times against configured SLA thresholds:

def compute_stage_sla(self, service_request) -> SLAResult:
    stage = service_request.current_stage
    sla_config = stage.sla_config

    elapsed_minutes = (timezone.now() - service_request.stage_entered_at).total_seconds() / 60
    target_minutes = float(sla_config.target_hours) * 60
    elapsed_pct = (elapsed_minutes / target_minutes * 100) if target_minutes > 0 else 0

    warn_pct = sla_config.warning_threshold_pct
    crit_pct = sla_config.critical_threshold_pct

    if elapsed_pct < warn_pct:
        risk = 'safe'
    elif elapsed_pct < crit_pct:
        risk = 'warning'
    elif elapsed_pct < 100:
        risk = 'critical'
    else:
        risk = 'breached'

    return SLAResult(risk_level=risk, elapsed_minutes=elapsed_minutes,
                     target_minutes=target_minutes, elapsed_pct=elapsed_pct)

Significance: Eliminates black-box opacity by computing deterministic SLA risk levels directly from configured thresholds and actual database timestamps.

7. LIMITATIONS

In accordance with academic integrity and rigorous engineering practices, the verified limitations of the current InsightFlow implementation are explicitly stated:

  • Local Database Scope: The current active database is SQLite 3 (db.sqlite3). While suitable for academic development, evaluation, and single-host demonstration, enterprise production concurrency requires activating the configured PostgreSQL database backend.
  • Polling-Based Notifications: In-app alerts are delivered via client-side interval polling rather than persistent full-duplex WebSocket connections (e.g., Django Channels).
  • Deterministic Predictive Heuristics: SLA risk scoring and completion forecasts utilize deterministic dwell velocity heuristics and queue congestion multipliers rather than trained machine learning models, as historical multi-year university dataset training was outside the semester project timeline.
  • Simulated Campus ERP Integration: The Campus ERP / Student Information System integration is implemented as an internal simulation service (ERPIntegrationService) rather than a live network socket connected to a proprietary university ERP database.
  • Local Evaluation Environment: Performance evaluation was conducted in local development environments. High-volume stress testing under thousands of concurrent requests was not performed.
